# 117 第二十轮 —— 2:1 全景实时预览打通（27–30fps，录制中边写边读）

日期：2026-11-26 21:40–22:10 CST
结论一句话：**相机在录制的同一时刻，PC 能实时拿到 2048×1024 双鱼眼，27–30fps，回读距离可压到 256KB（≈0.2s）。**

## 一、先纯正上一轮的错误认知

第十九轮（doc116）写的是：
> `.LRF` 的 mdat 载荷 = `DJI protobuf 元数据` + `AVCC NAL`，把 mdat 里从首 IDR 起的内容前置 SPS/PPS 就能解。

**“从头顺着吃”这件事是错的。** 这轮在完整的 68MB 段（`c69.LRF`）上量清了真实布局：

```
mdat =
  [大块 protobuf 头（含 dvtm_oq101.proto / 02.01.1 / Osmo 360 等字段）]
  [AVCC: SPS(18) + PPS(5) + IDR]         ← GOF 锚点
  [大量 slice 数据 与 小块 protobuf 交错]
  [AVCC: SPS(18) + PPS(5) + IDR]         ← 下一个 GOF 锚点（每 ~640KB 一个）
  ...
```

证据：`r153` 从锚点顺序吃，**117 个 GOF 全部“吃不满”** —— 第一个 IDR 之后立刻不是合法长度前缀，
而是一段 protobuf（`1a 90 06 0a 0a 08 01 10 …`）。所以“顺序吃 NAL”必然错位，这正是 r147 只出 1 帧的原因。

**新策略（r154/r155 定稿）**：
1. 先找 GOF 锚点：`SPS(8~64B) + PPS(4~32B) + IDR(2KB~400KB)` 三连（长度不写死，各段会变）；
2. 从锚点起把这三项交给解码器（每个 GOF 重新对齐，天然容错）；
3. 锚点之后**扫锚**而不是顺序吃：位置合法（4B 长度 + 类型 ∈ {1,5,6,7,8,9} + 长度在区间）就取，不合法的字节跳 1 字节 —— 相当于自动越过中间的 protobuf。

## 二、第二个关键坑：`-fflags nobuffer` 会吃掉 99% 的包

同一份喂给 ffmpeg 的字节流（16.4MB，539 NAL）：

| 参数 | 解出帧数 |
|---|---|
| `-fflags nobuffer` | **2 帧** |
| 默认 | **425 帧** |
| `-probesize 32 -analyzeduration 0` | **425 帧** |

而且 nobuffer 不报错，只刷 `no frame!` / `Invalid data found`，极具误导性。
**结论：管道喂裸 h264 时永远不要用 `-fflags nobuffer`，要低延迟就压 `probesize/analyzeduration`。**

## 五、已知限制（诚实记录）

1. **必须处于录制状态**：这条链消费的是 `.LRF`，不录就没有数据（这也是它能成立的原因：录制管线是唯一稳定可控的“开机键”）。
2. **磁盘在涨**：录制期间 `.OSV` 约 11MB/s、`.LRF` 约 1.2MB/s。跑 10 分钟 ≈ 7GB。用完记得停录。
3. 帧率上限受 `.LRF` 编码限制：**代理轨固定 29.97fps**，所以实时预览上限就是 30fps。想看 119.88fps 只能走 `.OSV`（那是离线/事后路径，见 `rammer/R01`）。
4. 每段开头 2 秒左右会“等锚点”（找不到 GOF 不出图），属正常冷启动。
5. 还没做的：把 tee 探针装进 `dji_media_server`，直接拿未编码帧（现在是“编码后再解”）。
