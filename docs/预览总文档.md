## 一、目标与验收口径

**目标**：让 PC（Windows）在不依赖手机 DJI Mimo App、不截屏、不拍屏的前提下，直接从大疆 Osmo 360
（Qualcomm QCS8550 / DJI 定制 Linux Debian）拿到**实时全景预览**，并在同一链路完成控制与实时音频。

**验收口径**（已按实际需求下调，不要求与手机端画质一致）：

1. 流畅（≈25 fps）
2. 不丢包（重复包 0、断流 0）
3. 不花屏（零丢包 + 关键帧正确）
4. 无空档（不存在“12 秒断一次”）

## 三、协议层（已完全解析）

### 3.1 传输头

- `[0:2]` 总长（LE）
- `[6]` = `0x05` 请求 / `0x04` ACK / `0x00` 保活
- 上行 magic `80 40 34`，下行 magic `80 0e 8a`

### 3.2 下行大包（1472 B）

```
[16] 类型（随会话变化 01/02/04/05…）
[17] 通道号
[18] 通道内序号
[19:23] == 00 00 00 01
[23:]  载荷（首字节常为 0xff）
```

剥壳规则：`payload = p[19:]`（当 `p[19:23]` 确为 `00000001`），否则 `p[20:]`。

### 3.3 内层 DUML

```
55 <len> <crc8> <app发送方> <recv> <seq 2B> <flags> <cmd_set> <cmd_id> <payload> <crc16>
```

`probe/lv_own.py` 内提供 `crc8c()` / `crc16m()` / `duml()` 可直接造包。

## 四、第一道墙：12 秒断流（已破解）

### 4.1 机理

`dji_sys` 内 `sys_host_check_status_ti` 判定“主机链路是否还在”，日志串：

```
HOST: %#x ping %#x error: %d retry times: %d
```

唯一引用点在 `0x5d2cc`。重试次数耗尽 → `sys_host_task_sm_down` → 会话被判死，正好 12 秒。

### 4.2 补丁

- 文件偏移 **`0x5d2f8`**
- 原值 `54 00 02 c1`（`b.ne`，条件跳转）
- 改为 `14 00 00 16`（无条件 `b`，永远走“继续”分支）

只改**运行中进程的内存**：

```python
base = 首个 /usr/bin/dji_sys 映射地址   # 从 /proc/<pid>/maps 取
addr = base + 0x5d2f8
open("/proc/<pid>/mem","rb+").seek(addr).write(b"\x14\x00\x00\x16")
```

**磁盘零改动**，回滚 = `systemctl restart dji_system`。

封装脚本 `probe/gate_off.py`（幂等，自带原值校验 `0x540002C1`）。

### 4.3 实测

| 时长 | 速率 | 结果 |
|---|---|---|
| 32 s / 78 s / 22 s / 30 s / 20 s | 600–666 包/秒（≈26 fps） | **零断流、重复包 0、无空档** |

## 五、第二道墙：解不出图（编码器不发 IDR）

### 5.1 现象

任何“事后接入”的会话，抓包里都**只有 P 帧**，没有 SPS/PPS/IDR → 解码器无法建立参考帧 → 全黑或纯噪点。

### 5.2 根因（日志直接给出）

```
[ djiwlc2venc ] print_c2_venc_property:  [liveview] wl_plugin config idr_interval : 1000000.
StandardCaps: IntraRefresh disabled: period=0.000000
QC2V4l2Codec: [avcE_93] unknown/unsupported param coding.sync-frame-interval index = 0x52002005
```

`idr_interval = 1000000` 意味着**永远不会再出 I 帧**——编码器只在**实例创建的第一帧**吐一个带 SPS 的 IDR，
之后永远只有 P 帧。

### 5.3 无效路线（记死，别再试）

- 改内存里 `idr_interval` 为 25（`probe/force_idr.py`）：配置**只在实例创建时读一次**，改后毫无效果。
- 改完再 `restart dji_camera3`：那个实例创建时配置还没被改，同样无效。
- 给旧 SPS 接新流：只能解出全黑（无 I 帧，P 帧无参考）。
- 自己用 x264 造各尺寸 SPS 硬拼：同样全黑。
- 各种 ACK 变体 / 补发命令 / 整包克隆真机 / 重叠接力 / 换源 IP / `kill -STOP` 冻线程（会把相机搞出 core dump）。

### 5.4 有效手法（本文档的核心）

> **先让客户端连上，再中途重启编码器进程**，让“实例创建”发生在有消费者在场时，
> 那个唯一的 IDR 就会被我们收到。

```bash
systemctl restart dji_sw_uav          # 让单客户端绑定让位给我们的客户端
sleep 3
tcpdump -i lo -n -s 0 -w /dev/shm/x.pcap udp &
python3 /data/local/tmp/lv_fix.py /dev/shm/mimo.pcap 32 20 &
sleep 6
systemctl restart dji_camera3         # ★关键：连接中重启
```

### 5.5 实测命中（`samples/sC.pcap`，21.4 MB / 22 s）

```
SPS  @ 6,210,886   00000001 67 64 00 28 ac b4 01 00 04 0d 35 …
PPS  @ 6,210,908   00000001 68 ee 06 f2 c0
IDR  @ 6,210,917   00000001 65 …
```

ffmpeg 直接解，零报错：

```
Stream #0:0: Video: h264 … 2048x1024, 25 fps
```

参数集与历史成功样本逐字节一致，说明**该预览档参数集固定，可复用**：

```
00000001 67640028 acb40100 040d3501 010106d0 a135
00000001 68 ee06f2c0
```

（31 字节，存为 `samples/sps_2048.h264`）

### 5.6 通道分布（同一份抓包）

| 通道 | 字节 | SPS | IDR | 含义 |
|---|---|---|---|---|
| 0x20 / 0xa0 / 0x22 / 0xa2 / 0x21 / 0xa1 | 各 1.8–1.97 MB | 无 | 无 | 全景 6000×3000 六分片 |
| 0x92 | 1.30 MB | 无 | 有（873,612） | 带 I 帧的路 |
| **0x0d** | 9,130 B | **有** | **有** | 2048×1024 预览小流 |

## 六、控制面：参数 / 模式 / 录像

`dji_cst` 是相机自带的用例执行器，用例库 **203 条**，覆盖度很高：

| 类别 | 可用序列（节选） |
|---|---|
| 参数 | `Binder_SetISO`、`SetShutterSpeed`、`SetExpoMode`、`test_3a_ISO_setting`、`test_3a_ev_setting`、`test_dzoom_*` |
| 模式 | `duss_mode_profile_switch`、`duss_cap_mode_switch`、`duss_rec_mode_switch`、`duss_pano_rec_mode_switch` |
| 预览档 | `duss_liveview_6000x3000_pano_video_p25`（长期使用，PASSED） |
| 录像 | `duss_record_*`（2688×1512 起，到 `7680x3840_video_pano_p60`），含低光/预录/长录/延时/子弹时间 |
| 拍照 | `osmo_shot`、`duss_single_capture_*`（含 4s/8s 长曝光） |

运行方式：

```bash
cd /usr/lib
LD_PRELOAD=/data/local/tmp/hk/libdcam_hook.so:libqcom_adapter.so \
  dji_cst -d cst -u -f -m <序列名> -l /tmp/x.log
```

判成败：`grep -a -E "CST_RLT|CST_Summary" /tmp/x.log`

**注意**：录像失败最常见的原因不是权限，而是存储。`/data` overlay 只有 94 MB，很容易被日志写满
（GUI 会报 `storage status[8 FULL]`）；SD 卡若未挂载会报“卡不存在”：

```bash
mkdir -p /mnt/media_rw/sd
mount -t exfat /dev/mmcblk1p1 /mnt/media_rw/sd
```

## 七、副作用与坑（务必先读）

| 操作 | 后果 | 回滚 |
|---|---|---|
| `systemctl restart dji_camera3` | 局部重启，安全 | 自动 |
| `systemctl restart dji_sw_uav` | 让出单客户端绑定，安全 | 自动 |
| `systemctl stop/start gui` | **会断 USB adb** | 需重插线并在屏幕选“文件传输” |
| `systemctl restart dji_media` | **整机 userspace 挂掉**：ping 通但 adbd/HTTP 全死，只能断电重开 | 物理断电 |
| 改 `/proc/<pid>/mem` | 只影响当前进程 | 重启对应服务即恢复 |
| `kill -STOP` 冻编码器线程 | 5.8 秒断流并产生 coredump | 不要做 |

抓包注意：

- **不要写 `/data`**（只剩十几 MB），写 `/dev/shm`
- `-w -` 不可用，必须落文件
- loopback 抓包 `linktype=1`，IP 从 `pp[14:]` 起

## 八、复现步骤（从零到出图）

```bash
# 0. 连接（USB 或网络 adb 192.168.31.100:5555）
adb devices

# 1. 打闸门补丁（每个新 boot 都要重打，因为只改内存）
python3 /data/local/tmp/gate_off.py

# 2. 让客户端先连上，再中途重启编码器，逼出 IDR
adb shell 'systemctl restart dji_sw_uav; sleep 3;
  tcpdump -i lo -n -s 0 -w /dev/shm/sX.pcap udp & sleep 1;
  (python3 -u /data/local/tmp/lv_fix.py /dev/shm/mimo.pcap 32 20 >/dev/shm/fx.log 2>&1 &);
  sleep 6; systemctl restart dji_camera3; sleep 24; kill %1'

# 3. 取回抓包
adb pull /dev/shm/sX.pcap samples/sX.pcap

# 4. 逐通道看谁带参数集
python probe/ch_sum.py samples/sX.pcap

# 5. 从 SPS 处切片并解码
python probe/cut_from.py samples/sX.pcap <SPS偏移>
ffmpeg -y -f h264 -i samples/_dec.h264 -vf "select='eq(n\,0)'" -fps_mode passthrough samples/out.png
```

## 十、为什么不用别的路

- **UVC**：早已验证走不通。
- **QMMF 机内直取**：`Camera service has died`。
- **RTMP 推流**：`set_mode_profile ret 214`。
- **USB 仅充电**：不枚举，反而失去 adb。
- **PC 连相机热点**：已被否决（改路由环境）。
