# Round 10 — Continuous stream unlocked and the default configuration finalized

> 2026-11-22. Goal: move from "can decode frames" to "frames keep coming". Standing result:
> the `live.bat` default configuration sustains continuous streaming without corruption, at
> 13–25 fps.

## 1. One-line conclusion

After fixing three things together, the camera no longer closes the stream at 45–55 s:

1. **Do not cut the tape** (`CUT=0`): the old default `CUT=7.0` also chopped off the
   cold-boot "switch app mode" ordering; it was part of the "dozen-frames ceiling".
2. **The cycle segment covers the healthy window** (`CYCLE_FROM=6.30`, `CYCLE_TO=54`,
   `LOOP_TO=54`); one cycle ≈47.7 s, repeated back to back, **including the tape's own
   ack/treq skeleton** (no longer stripped out).
3. **Clock restamp + correct ack** (`RESTAMP=1`, `ACK=1 ACK_MODE=clk`): each cycle
   recomputes the on-device clock offset from the camera's freshly sent 35B stream-check,
   instead of accumulating an estimate per cycle; ack uses a virtual client clock (the real
   ack is three samples of the same 2.34 MHz monotonic clock).

## 2. This round's measured A/B table (same camera, same up9004.bin)

| Config | Frames | Duration | Result |
|---|---|---|---|
| CUT=0 / LOOP=54 / no loop / no ack | 735 | ~48 s | Stops at tape end |
| CUT=0 / LOOP=45 / loop 6.3~45 / no ack | 783 | ~43 s | Stop point follows LOOP_TO |
| CUT=0 / LOOP=54 / no loop / no ack | 921 | ~53 s | Same as above |
| CUT=0 / LOOP=38 / loop 6.3~38 / RESTAMP / no ack | 668 | ~31 s | Stops earlier; shows "truncating" itself is harmful |
| **CUT=0 / LOOP=54 / no loop / ACK=clk / TREQ=0** | **949** | **>150 s** | **Did not die, but dropped to ~1 fps** |
| **CUT=0 / LOOP=54 / no loop / ACK=clk / TREQ=10** | **1208** | **>150 s** | Same; 17 fps for the first 55 s, then a trickle |
| **CUT=0 / LOOP=54 / loop 6.3~54 / RESTAMP / ACK=clk / TREQ=10** | **2720+ (still growing)** | **>150 s** | ✅ unlocked: steady 25 fps in the later segment |

Decisive contrast: **with ACK=0 the stream always stops near the tape end; after
ACK=clk it crosses the end and keeps receiving.** So the direct switch for the "16-frame
ceiling / 45 s drop-off" is ack correctness — not battery, not packet loss, not frame
reassembly.

## 4. Code changes

`probe/live_server.py`
1. `session_keeper()` loop body: when `span<=0.02`, the old code only set span to 1.0
   without pacing, so the "28880 repetitions of the 55-subscription cycle" flooded the
   camera UDP. Now spread one per 0.1 s.
2. New `LIVE_RESTAMP=1`: each cycle takes the three field pairs `ACK["last_chk"]` and
   `ACK["tpl"]`, differences medianed, as this cycle's delta (replacing the hard-coded
   `k*span*1000`).
3. New `LIVE_CYCLE_FROM=full|whole`: whole-tape loop mode (including opening mode packets
   and closing), for the "periodic preview reopen" experiment.
4. `ACK_MODE=clk` became the best measured setting (virtual 2.338e6 units/s client clock).

`osmo360/live.py`
1. `pkill -f 'live_serve[r].py'` (the old pattern matched the adb shell running the command
   itself, exit 143).
2. The default remote environment was switched wholesale to the round-10 winning combo
   (see §1), with the reason for each item written out.

## 7. Frame-drop attribution (r87 forensics + r88 A/B)

A 1500-packet forensic capture of the stable period (`samples/rt_now.bin`, dissected by
`tools/pc/r87_fragcov.py`, unpublished):

* Of the 30 frames on main base=0x1c, **100% contain (0,0)**, rank0 14 fragments / rank1
  13~14 fragments, gap=0. In other words **no fragments were lost during these 5 seconds**
  — the frame reassembly chain was clean.
* In the same window there were only 805 video packets ≥1000B (≈160/s), 27~28 packets per
  frame ⇒ **the camera itself sent only about 6 fps**.
* At the same time there were 432 35B stream-checks (≈86/s, normal 5/s), showing the
  camera aggressively retransmitting checks; but the `ack` count rose in step, i.e. we
  replied to every one.

`tools/pc/r88_ackmax.py` four ack-rate-limit A/B tiers (60 s each, same round-10 config):

| Tier | Frame increment | fps | ack/s |
|---|---|---|---|
| clk / unlimited (current) | +1000 | **16.7** | 58.2 |
| clk / cap 8Hz | +665 | 11.1 | 7.4 |
| clk / cap 3Hz | +950 | 15.8 | 2.9 |
| dup / cap 8Hz | +679 | 11.3 | 7.4 |

treq re-scanned at 15 / 20 / 30 Hz: 16.6 / 11.2 / 16.3 fps — **treq is no longer the
bottleneck; frame rate is independent of it**.

**Conclusion (the firmest attribution this round):**
1. Fragment loss / frame reassembly is not the bottleneck (0 fragments lost in the capture
   window, conceal=0);
2. Ack must not be rate-limited; **every check must be acknowledged** — limiting it drops
   fps to 11;
3. fps switches bimodally between 16.6 and 11.2, depending on which base is locked that time
   (`main=0x1e` vs `0x1c`): two or three encoder instances are alive inside the camera at
   once (residual from previous sessions); we recognize only one of them ÷ they each take
   encoder/send bandwidth. **One lane 16.7 fps + the other lane ~8 fps ≈ encoder total 25
   fps** — the numbers line up exactly;
4. To get the full 25 fps, the camera must have only one encoder instance alive. The only
   reliable means so far is **power-cycling the camera** (a software restart of
   `dji_camera3` only spawns another lane, it does not destroy the old one). This step must
   be done manually by the user.
