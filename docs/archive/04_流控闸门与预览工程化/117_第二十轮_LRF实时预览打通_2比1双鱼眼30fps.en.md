# 117 Round 20 — 2:1 panorama live preview unlocked (27–30 fps, read-while-recording)

Date: 2026-11-26 21:40–22:10 CST
One-line conclusion: **while the camera is recording, the PC can take a real-time 2048×1024
dual-fisheye picture at 27–30 fps; the read-back distance can be pressed down to 256 KB
(≈0.2 s).**

---

## 1. Correcting the previous round's wrong mental model

Round 19 (doc116) wrote:
> The `.LRF` mdat payload = `DJI protobuf metadata` + `AVCC NAL`; decoding works by
> prepending SPS/PPS to the content from the first IDR inside mdat.

**"Eat it sequentially from the head" is wrong.** This round measured the real layout on
a complete 68 MB segment (`c69.LRF`):

```
mdat =
  [large protobuf header (with dvtm_oq101.proto / 02.01.1 / Osmo 360 fields)]
  [AVCC: SPS(18) + PPS(5) + IDR]         ← GOF anchor
  [many slice bytes interleaved with small protobuf blocks]
  [AVCC: SPS(18) + PPS(5) + IDR]         ← next GOF anchor (~every 640 KB)
  ...
```

Evidence: `r153` (unpublished) eating in anchor order leaves **all 117 GOFs "incomplete"**
— right after the first IDR there is no legal length prefix; it is a protobuf block
(`1a 90 06 0a 0a 08 01 10 …`). So "eat NALs in order" necessarily misaligns; this is why
r147 produced only 1 frame.

**New strategy (finalized in r154/r155, both unpublished)**:
1. Find GOF anchors first: the triple `SPS(8~64B) + PPS(4~32B) + IDR(2KB~400KB)` (lengths
   are not hard-coded; they vary per segment);
2. From the anchor, hand these three to the decoder (realigned per GOF, naturally
   fault-tolerant);
3. After the anchor, **scan for anchors rather than eat in order**: take a position when it
   is legal (4B length + type ∈ {1,5,6,7,8,9} + length in range); skip 1 byte otherwise —
   equivalent to automatically stepping over the interleaved protobuf.

## 2. The second key trap: `-fflags nobuffer` eats 99% of packets

Same byte stream fed to ffmpeg (16.4 MB, 539 NALs):

| Flag | Frames decoded |
|---|---|
| `-fflags nobuffer` | **2 frames** |
| default | **425 frames** |
| `-probesize 32 -analyzeduration 0` | **425 frames** |

Moreover nobuffer does not error out; it only prints `no frame!` / `Invalid data found`,
which is highly misleading. **Conclusion: when piping raw h264, never use
`-fflags nobuffer`; if low latency is wanted, trim `probesize/analyzeduration`.**

## 5. Known limitations (honest record)

1. **Must be recording**: this chain consumes the `.LRF`; without recording there is no data
   (this is also why it works: the recording pipeline is the only stable, controllable
   "power-on key").
2. **Disk keeps growing**: during recording `.OSV` ≈11 MB/s, `.LRF` ≈1.2 MB/s. 10 minutes
   ≈7 GB. Remember to stop recording afterward.
3. Frame-rate ceiling is set by the `.LRF` encoding: the **proxy track is fixed at
   29.97 fps**, so the live preview caps at 30 fps. To see 119.88 fps you must go through the
   `.OSV` (that is an offline/post path, see `rammer/R01`).
4. The first ~2 seconds of each segment "waits for an anchor" (no picture until a GOF is
   found); this is normal cold start.
5. Not done yet: install the tee probe into `dji_media_server` to take unencoded frames
   directly (currently "encode first, decode after").
